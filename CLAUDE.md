# CLAUDE.md — точка входа в проект

**Wander** — кастомный файловый проводник для Windows 11 на WPF / .NET 10.
Альтернатива системному Explorer: убрать лишнее, починить его баги, добавить
удобств.

Это входной документ для работы над проектом (и для Claude Code при старте
сессии). Пользовательская витрина — в [README.md](README.md).

## Столпы проекта

1. **UX.** Смысл всего проекта — сделать проводник лучше встроенного: убрать
   лишнее (планшетоориентированные элементы Win11, навязчивые ссылки на
   OneDrive и 3д-объекты), починить баги Win11 Explorer (самосворачивающиеся
   ветки дерева, тормоза, потеря фокуса после операций), добавить удобств
   (навигация через отдельные поддеревья, детальный просмотр информации,
   чтение множества форматов).
2. **Надёжность.** Любая деструктивная операция (удаление, перемещение,
   перезапись, переименование системных путей) сопровождается диалогом
   подтверждения с **Cancel по-умолчанию**. Случайно снести системную папку не
   получится. Всё, кроме безвозвратного удаления, откатывается через `Ctrl+Z`.
3. **Интеграция с системой.** Wander — не изолированная песочница, а обычное
   windows-приложение среди остальных. По-умолчанию выбирается тот вариант,
   при котором обмен с системой и другими приложениями работает: общий буфер
   обмена, стандартные форматы drag & drop, системные ассоциации и меню,
   привычные хоткеи. «Сделаем своё внутри, наружу не выпустим» — это всегда
   осознанная уступка, а не путь по-умолчанию.

   **Если такая уступка всё же нужна** (сложно, дорого, рискованно) — она не
   принимается молча: причина и цена выносятся на обсуждение, а решение и
   разобранные варианты записываются в [BACKLOG.md](docs/BACKLOG.md). Если по
   ходу работы обнаружилось, что интеграция где-то не работает, — это тоже
   повод остановиться и вынести вопрос, а не «оставить как есть». Разобранный
   пример такой записи — «Буфер обмена» в бэклоге.

## Архитектурные правила

Детали и схемы механизмов — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
Здесь только то, что нельзя нарушать:

- `Wander.Core` не зависит от Windows и от UI. Никаких `using System.Windows.*`,
  никаких COM/PInvoke. Понадобилось — значит нужен интерфейс в Core и
  реализация в `Wander.Platform.Windows`.
- WPF — отвинчиваемый слой: ViewModel'и дёргают сервисы Core через
  `ServiceLocator`, никакой WPF-специфики в Core.
- Точка композиции одна: `App.OnStartup` → `PlatformBootstrapper.RegisterDefaults()`.
- Service Locator вместо DI-контейнера. Простой статический локатор — не
  подключать `Microsoft.Extensions.DependencyInjection` и прочее.
- Без MVVM-фреймворков: ни CommunityToolkit.Mvvm, ни ModernWpfUI/MahApps.
- Тесты — только для Core, через фейки из `tests/Wander.Core.Tests/Fakes/`.
- Минимализм: связь UI ↔ логика минимальным понятным срезом, никаких
  преждевременных абстракций.
- **Сложность выносится туда, где её достаёт тест** (принято 2026-09-01).
  Машина состояний или вычислимое правило — листинг, намерения выделения,
  геометрия раскладки, решения сторожа — живёт в Core за чистым контрактом
  (факты на входе, решения на выходе), а вью и code-behind исполняют
  решения. Инвариант, который проверяется только руками, ломается третьим
  фиксом подряд (см. MANUAL-CHECKS «Скорость и отзывчивость»). Прецеденты:
  `TileLayout`, `FolderChanges`, «сессия папки» (PLAN, шаг O11).

**Список не дёргается от изменения параметров.** Правка того, что показано
*внутри* строки — оценка, цветная метка, любой будущий флаг — не имеет права
пересобирать папку: ни перечитывания листинга, ни потери выделения, ни потери
фокуса, ни пересортировки под курсором.

Пересборка листинга допустима только тогда, когда изменился **состав** папки:
файлы появились, исчезли или переименовались. «Заодно обновим всё» — это не
осторожность, это баг: пользователь видит, как страница прыгает в ответ на
щелчок по звезде.

Держится это тремя вещами, и все три обязательны:

- **Сторож папки говорит, что именно изменилось** (`DirectoryChange`:
  путь + «изменился ли состав»), а `MainViewModel` отвечает выборочно —
  либо `Refresh()`, либо перечитывание затронутых строк. Решение принимает
  сессия папки в Core (`FolderSession.DecideWatchTick` поверх
  `FolderChanges`), потому что это и есть суть правила.
- **Замена строки не теряет выделение.** `FileSystemEntry` — record, править
  на месте нельзя, поэтому любая правка заменяет объект, а список выкидывает
  заменённый объект из выделения. `ReconcileEntries` оборачивает **каждую**
  пересборку `Entries` и возвращает выделение без прокрутки и без переноса
  фокуса.
- **Служебные файлы не считаются изменениями.** `TransientFiles` — и наш
  `.wander-tmp`, и виндовый `~RF….TMP`, который `File.Replace` создаёт сам.
  Без этого каждая запись оценки выглядела как «в папке появился и исчез
  файл», то есть как изменение состава.

То же самое относится к `Ctrl+Z` такой правки — см.
`IUndoableAction.MetadataTargets`.

**Любая новая операция с файлами обязана:** пройти `SystemPathGuard`,
залогироваться, положить `IUndoableAction` в `UndoService`, и — если
деструктивна — спросить подтверждение с Cancel по-умолчанию. Отступление от
любого из пунктов — осознанное и записанное в доке рядом с кодом, а не
«забыли» (разобранный пример — восстановление из корзины без undo,
см. [ARCHITECTURE.md](docs/ARCHITECTURE.md)).

**Пользовательский текст — только через ресурсы.** Ни одной новой строки,
которую читает пользователь, в коде и XAML: всё в
`src/Wander.App/Resources/Strings.resx`. Core просит текст через
`ITextSource` — ссылки на App у него нет и быть не должно.

## Проверка

Канонический и единственный способ — из **PowerShell**, из корня репозитория:

```pwsh
.\tools\check.bat
```

| Аргумент | Что делает |
|---|---|
| *(без аргументов)* | build → `dotnet format --verify-no-changes` → сверка строк → тесты |
| `run` | то же + smoke-запуск приложения (окно за экраном, само закрывается) |
| `format` | применяет форматирование (**пишет файлы**) |

Шаг «строки» — `tools\check-strings.ps1`: сверяет ключи ресурсов в коде и
XAML с `Strings.resx` в обе стороны. Тесты сюда не дотягиваются (они покрывают
только Core), а опечатка в ключе компилируется молча и всплывает уже
в интерфейсе — вместо подписи виден сам ключ.

Exit code 0 — всё зелено; иначе код первого упавшего шага.

> **Не запускать через `cmd /c` из bash.** `cmd /c "tools\check.bat"` возвращает
> exit 0, но глотает вывод build/format/tests — «успех» в этом случае ничего не
> значит и скрывает реальные падения. Только `.\tools\check.bat` из PowerShell.

Точечно во время отладки можно дёргать `dotnet build` / `dotnet test` напрямую
(`dotnet` есть в PATH), но **перед коммитом — полный `.\tools\check.bat`**.

### Метрики структуры — `tools\metrics.ps1`

Не проверка, а измерение: строки по проектам, самые большие файлы, публичная
поверхность Core, места `ServiceLocator.IsRegistered`, самые длинные методы,
самая глубокая вложенность, число `using` на файл.

```pwsh
.\tools\metrics.ps1                 # отчёт на экран
.\tools\metrics.ps1 -Out before.txt # ещё и в файл
```

Нужен техническим чисткам: снимки «до» и «после» обязаны быть **одним и тем
же измерением**, иначе сравнивать нечего, а «стало чище» — не результат.
Разбор внутри — грубый сканер скобок, а не парсер C#: абсолютной точности
он не даёт и не должен, важна повторяемость.

### Граф зависимостей — `tools\deps.ps1`

Свод `using`-ов по папкам: рёбра «от → к», уровни, циклы. Правило «между
папками нет циклов» и сгенерированный снимок живут в
[ARCHITECTURE.md](docs/ARCHITECTURE.md), «Граф зависимостей между папками»;
`.\tools\deps.ps1 -UpdateDoc` перезаписывает блок там после правок,
задевших `using`-ы или раскладку файлов.

### Экран и ввод — не трогать

**Claude не эмулирует ввод и не выводит окна поверх экрана.** Никаких
`SetCursorPos` / `mouse_event` / `SendKeys` / `SetForegroundWindow`, никаких
кликов «чтобы проверить». На том же экране параллельно работает человек, и
перехваченный курсор — это чужие клики, попадающие не туда.

Это **не** относится к `.\tools\check.bat run`: smoke-запуск идёт с ключом
`--smoke`, при котором окно поднимается за пределами экрана, не забирает
фокус, не появляется в панели задач и само закрывается через пару секунд.
Ничего на чужом экране не двигается, так что этот прогон Claude делает сам —
и обязан делать при финализации скоупа.

Чем проверять вместо этого:

- сборка, тесты, `tools\check-strings.ps1`;
- логи сессии — `%LOCALAPPDATA%\Wander\logs`;
- отдельный консольный харнесс в scratchpad, который дёргает нужный класс
  напрямую (так проверялись `VirtualizingWrapPanel` и разбор ориентации
  в CR3 — оба нашли настоящие баги без единого клика);
- для зависаний интерфейса — тот же харнесс, но с **настоящим окном за
  пределами экрана** (`Left = -32000`, `ShowActivated = false`) и
  подменённым `IAppStateStore`, чтобы не трогать чужой `state.json`.
  Жесты подаются на UI-поток, сторожевой поток считает проходы раскладки:
  счётчик не останавливается — значит окно заклинило. Так был найден
  дребезг размера ячейки в плиточных режимах.

Что проверить нельзя — **выписывается в отчёт списком**, человек прокликает
сам. Честный список лучше молчаливого «вроде работает».

Текущее состояние: **870 тестов зелёных**, формат чистый, 426 строк
интерфейса в ресурсах. Два теста,
которые были нестабильны (`SearchControllerTests.Reset_ClearsQuery_WithoutFiringFilteredAgain`
и `UndoServiceTests.BeginOperation_ConcurrentOps_RaceFree_OnUndoVisibility`),
починены 2026-08-25: обе гонки были в самих тестах, ожидание по таймауту
заменено на детерминированный сигнал.

## Git — только чтение

**Claude выполняет исключительно читающие и проверяющие git-команды.** Стейдж,
коммит и вообще всё мутирующее делает человек.

| Можно | Нельзя без явной просьбы |
|---|---|
| `git status`, `git log`, `git diff`, `git show` | `git add`, `git stage` |
| `git ls-files`, `git ls-tree`, `git blame` | `git commit`, `git revert`, `git reset` |
| `git check-ignore`, `git tag` (список) | `git tag <имя>`, `git push`, `git pull` |
| | `git mv`, `git rm`, `git checkout`, `git restore` |
| | `git branch`, `git merge`, `git rebase`, `git stash` |

Это относится и к командам, которые мутируют индекс «заодно»: `git mv` вместо
переименования файла, `git rm --cached` вместо правки `.gitignore`. Нужно
переместить файл — обычное перемещение на файловой системе, гит сам увидит
rename по содержимому.

Результат работы оставляется в рабочем дереве незастейдженным, а в отчёте
перечисляется, что изменилось — решение, что из этого коммитить, за человеком.

То же касается скриптов в `tools\`: они правят файлы и печатают git-команды
как следующий шаг, но не выполняют их (см. [RELEASING.md](docs/RELEASING.md)).

## Кодстиль

Зафиксирован в [`.editorconfig`](.editorconfig) — `dotnet format` подхватит все
правила автоматически. Краткая выжимка:

- **1TBS** (Egyptian / One True Brace Style): `{` на той же строке,
  `} else {`, `} catch {`, `} finally {`.
- **Braces обязательны** для всех `if/for/while/foreach`, даже однострочных.
- **File-scoped namespaces**: `namespace Wander.Core.FileSystem;`.
- **Namespaces по доменам**: `Wander.<модуль>.<раздел>`, без излишней вложенности.
- **var** — где тип понятен из выражения; **явный тип** для примитивов.
- **`_camelCase`** для private полей; **PascalCase** для констант, свойств,
  методов и типов.
- **Отступ** — 4 пробела, не табы.
- **Пустая строка** после `return` / `continue` / `break` внутри метода и между
  логически разными блоками; **две пустые строки** между полями и методами.
- **В комментариях кода — только обычные ASCII-знаки**: дефис `-`, кавычки
  `"`, стрелка `->`, `...`. Никаких типографских тире, стрелок и буллетов —
  их не набирают с клавиатуры, в диффе `-` от `—` не отличить, и однажды
  они уже превратились в кашу при пересохранении файла не тем инструментом
  (2026-09-01). Типографике место в маркдаун-доках и в `Strings.resx`, не
  в коде.

## Roadmap

Крупные направления продукта. Что осознанно отложено:

- **Тёмная тема.** Первый кусок уже стоит: галерея и панель просмотра
  берут цвета из палитры области контента (`GalleryBackground` +
  `GalleryPalette` — фон, подписи, выделение, ховер), а не из одного
  захардкоженного цвета. Расширять оттуда, а не начинать заново.
- **Фильтры поиска по дате, размеру и regex.** Сам поиск сделан: окно с
  маской имени и текстом внутри файлов (через «и»), вайлдкарты, рекурсия
  по подпапкам, автозапуск. Фильтр по типу закрыт маской; осталась форма
  для диапазонов — она же нужна фильтру по ISO / выдержке (PLAN, J3-хвост),
  и делать её стоит один раз на обе.
- **Плагины** — кастомные поведения, если идея зайдёт.
- **Symlinks / junctions / hard links** — сейчас только `.lnk`.

**Вкладки** переехали из Roadmap в [BACKLOG.md](docs/BACKLOG.md) 2026-08-27:
это уже не «пойдём в эту сторону», а вопрос «нужны ли они здесь вообще» —
разделение внимания между папками у нас решают дерево, закладки и история.
Практическое следствие: цифры под `Ctrl` свободны и заняты областями окна.

Уже закрыто и убрано из Roadmap: режим галереи с автовключением в папках
со снимками, фильтром по оценкам и созданием сайдкара по подтверждению
(`ImageFolderProbe`, `RatingFilter`, `CompanionMetadataService`, секция J
плана), связанные файлы — спутники (`.meta`, `.pp3`)
показываются одной строкой с основным файлом и переезжают/удаляются вместе
с ним (`Wander.Core/Companions/`, секция I в PLAN.md), контекстное меню в духе
Win10 с пунктами сторонних приложений и гибким выключением
(`ContextMenuBuilder` + `IShellContextMenu`), guard на системные пути
(`SystemPathGuard`),
undo через `Ctrl+Z`, drag & drop внутрь и наружу, async-операции с прогрессом и
отменой, поиск (маска имени и текст внутри файлов через «и», вайлдкарты,
рекурсия по подпапкам, отдельное окно с автозапуском —
`Wander.Core/Search/`, секция G плана), корзина внутри Wander, стабильное дерево без
самосворачивания, общий с системой буфер обмена (`ISystemClipboard`) и
самообновляющийся список (`IDirectoryWatcher`).
