# Wander — процедура релиза

Этот документ — последний шаг, механика выпуска. До него идёт **подготовка
к релизу** ([WORKFLOW.md](WORKFLOW.md)): хвосты, критичные баги, полный
набор автотестов, живой прогон, замеры версии, вердикт. Без зелёного света
оттуда сюда не заходят.

## Коротко

```pwsh
.\tools\publish.ps1 -Run     # релизный exe, погонять руками
# прочитать замеры из логов этого прогона (см. ниже)
.\tools\release-metrics.ps1 -Version 0.3.0   # снимок версии в docs/measurements/
.\tools\version.ps1 0.3.0     # поднять версию везде
# заполнить TODO в docs/CHANGELOG.md, сверить README
.\tools\check.bat
git commit -am "Релиз 0.3.0-бета"
git tag v0.3.0
git push origin master --follow-tags
```

Пуш тега `v*` запускает `release.yml` — CI собирает и публикует сам.

## Версия — в четырёх местах, трёх форматах

| Где | Для 0.3.0 | Зачем так |
|---|---|---|
| `Directory.Build.props` → `Version` | `0.3.0` | NuGet-совместимая, без суффикса |
| → `InformationalVersion` | `0.3.0-beta` | свойства exe, заголовок лога |
| → `FileVersion` | `0.3.0.0` | Win32-ресурс, четыре числа |
| git tag | `v0.3.0` | **без** `-beta`, CI-триггер |
| `CHANGELOG.md` заголовок и сноска | `[0.3.0-beta]` → `…/tag/v0.3.0` | Keep a Changelog |

`AssemblyVersion` **не трогать** — приколочен к `0.0.0.0` как
binding-идентичность; скрипт его не меняет.

## Скрипты

- `tools\publish.ps1 [-Run]` — тот же набор ключей, что у CI (Release,
  win-x64, self-contained, один файл, сжатие); печатает размер и SHA256.
  `dotnet run` и Rider дают Debug — стартует медленнее и ведёт себя иначе.
  В Rider — конфигурации «Publish release exe» и «Run release exe».
- `tools\version.ps1 <MAJOR.MINOR.PATCH> [-Suffix rc1|''] [-DryRun]` —
  проставляет три поля в `Directory.Build.props`, вставляет в CHANGELOG
  секцию с датой и заготовками `### Added` / `### Fixed` (`TODO`), добавляет
  сноску на будущий Release, печатает ручные шаги. Не коммитит, не тегает,
  не пушит. Падает, если версия не в формате, секция уже есть или якоря в
  файлах не найдены.

## Замеры перед релизом

Логи сессий — единственный источник про поведение у живого пользователя на
живых папках; после релиза те же цифры становятся багом. **Только на
релизной сборке** (`publish.ps1 -Run`): Debug несравним с PERFORMANCE.md.
Погонять минут десять по своим папкам с галереей и просмотром, читать логи
**этого** прогона (`%LOCALAPPDATA%\Wander\logs`):

| Строка | О чём | Плохо |
|---|---|---|
| `Startup: first frame N ms` | первый кадр | заметно хуже PERFORMANCE |
| `PERF ui.stall` | UI не рисовал | одиночные > 400 мс, частые > 100 |
| `PERF bg.*` | фон: миниатюры, обложки, shell | новая категория |
| `Folder listed in N ms` | медленное перечисление | секунды на сотнях файлов |
| `WARN` / `ERROR` | что пошло не так | повторяющаяся строка |

Смотреть ворох сессий: одна медленная — холодный кэш, десять — регрессия.

```pwsh
Get-ChildItem "$env:LOCALAPPDATA\Wander\logs" | Sort-Object LastWriteTime -Descending | Select-Object -First 40 | Select-String "first frame|PERF |WARN|ERROR" | ForEach-Object { $_.Line }
```

Решение по каждой находке: подтверждает PERFORMANCE — обновить там дату и
значения; регрессия — блокер релиза; медленно, но всегда так — TECHDEBT /
BACKLOG с цифрой; повторяющийся `WARN` / `ERROR` — разобрать до релиза.

**Снимок версии — отдельным файлом.** `tools\release-metrics.ps1 -Version
X.Y.Z` собирает окружение, вес и SHA256, старт и `PERF` из логов этого
прогона, память и GC по сценариям харнесса в `docs/measurements/X.Y.Z.md`;
«Verdict» там дописывается руками. Файл на версию не переписывается — это
то, чем через год отвечают на «когда стало медленнее». Правила —
[docs/measurements/README.md](measurements/README.md).

## Полная процедура

0. Подготовка к релизу пройдена и дала зелёный свет (WORKFLOW.md).
1. `.\tools\publish.ps1 -Run`, погонять. Прогон того же дня засчитывается
   (коммит в логе отстаёт на один — норма).
2. Прочитать замеры и снять снимок версии:
   `.\tools\release-metrics.ps1 -Version <версия>`, заполнить «Verdict».
   Регрессия останавливает релиз.
3. `.\tools\check.bat` — master зелёный.
4. `.\tools\version.ps1 <версия>`.
5. CHANGELOG: заменить `TODO`; секции Keep a Changelog (`Added`, `Changed`,
   `Deprecated`, `Removed`, `Fixed`, `Security`), лишние удалить.
6. README: плашка `**Beta X.Y**`, список «Что умеет» (появившееся дописать,
   исчезнувшее и «в планах» про сделанное убрать), подписи к скриншотам.
   Бейдж и ссылка на релиз динамические — не трогать.
7. `.\tools\check.bat` ещё раз — версия участвует в сборке.
8. `.\tools\publish.ps1` — последний взгляд на то, что уйдёт: путь, размер,
   SHA256.
9. Коммит, тег, пуш (блок «Коротко»). **Только человек**: пуш тега — это
   публикация, тихо откатить нельзя. Ассистент доводит до «осталось
   закоммитить» и останавливается; переспрашивать не нужно.
10. Проследить за CI (*Actions*); на странице релиза — `Wander.exe` и
    `Wander.exe.sha256`.

## Что делает CI

`.github/workflows/release.yml`, триггер — тег `v*`: `windows-latest`,
.NET 10 SDK; `dotnet publish` Release / win-x64 / self-contained /
single-file / сжатый; SHA256 рядом; `gh release create --generate-notes
--prerelease`. Сборка на раннере GitHub из публичного исходника — логи
открыты, SHA256 подтверждает, что exe собран из этого кода (часть обещания
README). `PublishTrimmed` для WPF не поддерживается — не включать.

## Локальные ограничения

- `gh` на машине не установлен — релиз только пушем тега; чинить вручную —
  `winget install GitHub.cli`.
- `.ps1` в `tools\` без BOM: PowerShell 5.1 читает их как ANSI, кириллица
  **только в комментариях**, литералы и вывод — ASCII.

## Если что-то пошло не так

- **Тег запушен, CI упал**: починить, переставить тег
  (`git tag -d v0.3.0; git push origin :refs/tags/v0.3.0`, исправить,
  затегать, запушить). Если релиз уже скачивали — лучше `0.3.1`.
- **Версия разъехалась**: прогнать `version.ps1` ещё раз — props
  проставит; секцию CHANGELOG поправить руками (повтор на ту же версию
  запрещён намеренно).
