# Wander — процедура релиза

Как выпустить версию. Точка входа во всю документацию —
[CLAUDE.md](../CLAUDE.md).

---

## Коротко

```pwsh
.\tools\publish.ps1 -Run     # собрать релизный exe и погонять руками
# прочитать замеры из логов этого прогона   (см. «Замеры перед релизом»)
.\tools\version.ps1 0.3.0     # поднять версию во всех местах
# заполнить TODO в docs/CHANGELOG.md
# сверить README: плашка Beta X.Y и список «Что умеет»
.\tools\check.bat             # build + format + tests
git commit -am "Релиз 0.3.0-бета"
git tag v0.3.0
git push origin master --follow-tags
```

Пуш тега `v*` запускает [release.yml](../.github/workflows/release.yml) —
дальше CI собирает и публикует всё сам.

---

## Почему нужен скрипт

Версия продублирована в **четырёх местах, в трёх разных форматах**, и они
расходятся намеренно. Руками это ошибка, ждущая своего часа:

| Где | Значение для 0.3.0 | Зачем именно так |
|---|---|---|
| `Directory.Build.props` → `Version` | `0.3.0` | NuGet-совместимая, без суффикса |
| `Directory.Build.props` → `InformationalVersion` | `0.3.0-beta` | то, что видно в свойствах exe и в заголовке лога |
| `Directory.Build.props` → `FileVersion` | `0.3.0.0` | Win32-ресурс, всегда четыре числа |
| git tag | `v0.3.0` | **без** `-beta`; на него смотрит CI-триггер |
| `docs/CHANGELOG.md` заголовок | `[0.3.0-beta]` | Keep a Changelog |
| `docs/CHANGELOG.md` сноска | `[0.3.0-beta]: …/tag/v0.3.0` | связывает заголовок с тегом |

> ⚠️ **`AssemblyVersion` не трогать.** Он намеренно приколочен к `0.0.0.0` —
> это binding-идентичность сборки. Если начать его двигать, каждая версия
> станет несовместимой по binding'у с предыдущей. Скрипт его не меняет,
> и руками тоже не надо.

## `tools\publish.ps1`

```pwsh
.\tools\publish.ps1          # собрать publish\Wander.exe, напечатать размер и SHA256
.\tools\publish.ps1 -Run     # то же и сразу запустить
```

Тот же набор ключей, что у CI: Release, win-x64, self-contained, один файл,
со сжатием. Отличие от `dotnet run` и от запуска из Rider принципиальное —
там Debug, а он стартует медленнее и ведёт себя иначе под нагрузкой.
Пощупать «как у людей» можно только этим.

В Rider — две конфигурации в выпадающем списке: «Publish release exe»
(только собрать) и «Run release exe» (собрать и запустить).

---

## `tools\version.ps1`

```pwsh
.\tools\version.ps1 0.3.0                # -> 0.3.0-beta
.\tools\version.ps1 0.3.0 -Suffix rc1    # -> 0.3.0-rc1
.\tools\version.ps1 1.0.0 -Suffix ''     # -> 1.0.0, без суффикса
.\tools\version.ps1 0.3.0 -DryRun        # показать план, ничего не писать
```

Что делает:

1. Проставляет `Version` / `InformationalVersion` / `FileVersion` в
   `Directory.Build.props`. `AssemblyVersion` не трогает.
2. Вставляет в `docs/CHANGELOG.md` новую секцию с сегодняшней датой и
   заготовками `### Added` / `### Fixed` с пометкой `TODO`.
3. Добавляет ссылку-сноску на будущий GitHub Release.
4. Печатает оставшиеся ручные шаги.

Чего **не** делает — намеренно: не коммитит, не ставит теги, не пушит.
Git-команды остаются за человеком.

Скрипт падает с внятной ошибкой, если версия не в формате `MAJOR.MINOR.PATCH`,
если такая секция в CHANGELOG уже есть, или если формат `Directory.Build.props` /
`CHANGELOG.md` разъехался и якоря не находятся. Молча разъехавшаяся версия
хуже явной ошибки.

## Замеры перед релизом

Логи сессий за время работы над версией — единственный источник, который
говорит, как приложение вело себя **у живого пользователя, на живых
папках**, а не на синтетике. Читать их надо до того, как версия уедет:
после релиза те же цифры превращаются в отчёт о баге.

> ⚠️ **Мерить только на релизной сборке.** Debug из Rider стартует заметно
> медленнее и подвисает чаще — сравнивать его цифры с
> [PERFORMANCE.md](PERFORMANCE.md) бессмысленно, там числа с
> опубликованного exe. Поэтому первый шаг процедуры — `publish.ps1 -Run`
> (или конфигурация «Run release exe» в Rider): собирает ровно тот
> одиночный self-contained exe, что уйдёт в релиз, от текущего коммита, и
> сразу запускает его. Погонять руками десять минут — по своим папкам, с
> галереей и просмотром — и читать логи **этого** прогона.

Логи лежат в `%LOCALAPPDATA%\Wander\logs`, по файлу на сессию. Что оттуда
брать:

| Строка в логе | О чём она | Что считать плохим |
|---|---|---|
| `Startup: first frame N ms` | время до первого кадра | заметно хуже, чем в [PERFORMANCE.md](PERFORMANCE.md) |
| `PERF ui.stall` | UI-поток не рисовал | одиночные всплески за 400 мс, частые за 100 мс |
| `PERF bg.*` | фоновая работа: миниатюры, обложки, shell | категория, которой раньше не было в списке |
| `Folder listed in N ms` | медленное перечисление папки | секунды на папке в пару сотен файлов |
| `WARN` / `ERROR` | всё, что пошло не так | любая повторяющаяся строка |

Смотреть не одну сессию, а весь ворох: одна медленная сессия — это
холодный кэш, десять — это регрессия. Полезная выжимка (из PowerShell,
из корня репозитория):

```pwsh
Get-ChildItem "$env:LOCALAPPDATA\Wander\logs" | Sort-Object LastWriteTime -Descending | Select-Object -First 40 | Select-String "first frame|PERF |WARN|ERROR" | ForEach-Object { $_.Line }
```

Итог этого прохода — не «посмотрели», а решение по каждой находке:

- **Цифры подтверждают то, что записано в [PERFORMANCE.md](PERFORMANCE.md)** —
  обновить там дату и значения, если они разошлись.
- **Регрессия относительно прошлой версии** — это блокер релиза, а не
  строка в бэклоге: пользователь получит её вместе с фичами.
- **Медленно, но так было всегда** — в [TECHDEBT.md](TECHDEBT.md) или
  [BACKLOG.md](BACKLOG.md), с цифрой из лога рядом.
- **`WARN` / `ERROR`, который повторяется** — разобрать до релиза. Ошибка,
  которую видно в каждой сессии, к следующей версии станет фоном, который
  никто не читает.

## Полная процедура

1. **Собрать релизный exe и погонять руками** — `.\tools\publish.ps1 -Run`,
   в Rider — конфигурация «Run release exe». Ровно то, что получит
   пользователь, от текущего коммита.

   Прогон **того же дня засчитывается**: если exe уже гоняли руками
   сегодня и логи этого прогона лежат в `%LOCALAPPDATA%\Wander\logs`,
   повторять не надо — берём замеры оттуда и идём дальше. Пуш обычно
   случается после прогона, так что коммит в строке лога отстаёт от
   текущего на один; это норма, а не повод перепрогонять.
2. **Прочитать замеры из логов этого прогона** — раздел «Замеры перед
   релизом» выше. Регрессия здесь останавливает релиз.
3. **Убедиться, что master зелёный** — `.\tools\check.bat`.
4. **Поднять версию** — `.\tools\version.ps1 <версия>`.
5. **Заполнить CHANGELOG.** Заменить `TODO` реальными пунктами. Секции по
   Keep a Changelog: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`,
   `Security`. Лишние — удалить.
6. **Сверить README.** Это витрина: её читают до того, как скачают, и
   врёт она молча. Пройти по трём местам — плашка `**Beta X.Y**` под
   скриншотом, список «Что умеет» (появившееся дописать, исчезнувшее
   убрать, «в планах» про уже сделанное — снять) и подписи к скриншотам,
   если интерфейс на них изменился. Ссылка на релиз и бейдж версии
   динамические (`releases/latest`) — их править не надо, и ждать сборки
   CI ради README тоже: правка едет тем же коммитом, что и тег.
7. **Проверить ещё раз** — `.\tools\check.bat`. Версия участвует в сборке,
   так что прогон после бампа не формальность.
8. **Пересобрать exe с новой версией** — `.\tools\publish.ps1` (или
   «Publish release exe» в Rider). Печатает путь, размер и SHA256; версия
   уже вшита, так что это последний взгляд на то, что уйдёт людям.
9. **Закоммитить, затегать, запушить:**
   ```pwsh
   git commit -am "Релиз 0.3.0-бета"
   git tag v0.3.0
   git push origin master --follow-tags
   ```
   `--follow-tags` отправляет и коммит, и тег одним движением.

   **Этот шаг делает человек, и только человек.** Не только потому, что
   git у ассистента на чтение (см. [CLAUDE.md](../CLAUDE.md)), а потому,
   что пуш тега `v*` — это и есть публикация: CI собирает и выкладывает
   GitHub Release, а тихо откатить его уже нельзя. Ассистент и скрипты
   доводят дерево до состояния «осталось закоммитить» и останавливаются
   здесь. Переспрашивать каждый релиз не нужно — ответ записан.
10. **Проследить за CI** — вкладка *Actions*. Workflow соберёт
    self-contained exe, посчитает SHA256 и создаст GitHub Release
    (`--prerelease`, notes генерируются автоматически).
11. **Проверить релиз** — на странице релиза должны лежать `Wander.exe` и
    `Wander.exe.sha256`.

## Что делает CI

[`.github/workflows/release.yml`](../.github/workflows/release.yml), триггер —
пуш тега `v*`:

1. `windows-latest`, .NET 10 SDK.
2. `dotnet publish` — Release, win-x64, self-contained, single-file, сжатый.
3. Считает SHA256, кладёт рядом в `Wander.exe.sha256`.
4. `gh release create` с обоими файлами, `--generate-notes --prerelease`.

Сборка идёт на раннере GitHub из публичного исходника — логи открыты, и
SHA256 позволяет любому убедиться, что скачанный exe собран из этого кода.
Это часть обещания в README про отсутствие вредоносного кода, а не просто
удобство.

> `PublishTrimmed` для WPF не поддерживается — не включать ни здесь, ни в
> `publish.ps1`.

## Локальные ограничения окружения

- **`gh` не установлен на машине разработки.** Значит релиз создаётся только
  пушем тега — руками `gh release create` не выйдет. Если понадобится
  чинить релиз вручную, `gh` придётся поставить
  (`winget install GitHub.cli`).
- **`.ps1` в `tools\` без UTF-8 BOM.** Windows PowerShell 5.1 без BOM читает
  скрипт как ANSI, поэтому кириллица в этих файлах допустима **только в
  комментариях**. Любой строковый литерал и вывод — ASCII/английский, иначе
  скрипт разваливается на разборе. Это касается и `version.ps1`, и
  `publish.ps1`.

## Если что-то пошло не так

- **Тег запушен, а CI упал.** Починить, потом переставить тег:
  ```pwsh
  git tag -d v0.3.0
  git push origin :refs/tags/v0.3.0
  # исправить, закоммитить
  git tag v0.3.0
  git push origin master --follow-tags
  ```
  Пока релиз не разошёлся по людям, это безопасно. Если по нему уже успели
  скачать — лучше выпустить `0.3.1`, чем переписывать историю.
- **Версия разъехалась между файлами.** Прогнать `version.ps1` с нужной
  версией ещё раз: он проставит `Directory.Build.props` заново. Секцию
  CHANGELOG при этом придётся поправить руками — повторный запуск на ту же
  версию скрипт намеренно запрещает, чтобы не плодить дубли.
