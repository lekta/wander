### K. Надёжное копирование больших файлов — [P2/P3, исследование]

Внешний движок для тяжёлых случаев (десятки ГБ, нестабильная сеть,
съёмные). Кандидаты: **robocopy** (встроен; retry `/R /W`, restartable
`/Z`, `/MT`, длинные пути, внятные коды), **FastCopy** — референс по своим
буферам и обходу системного кэша, не зависимость (лицензию проверить),
**certutil -hashfile** — verify-after-copy по флагу (для больших файлов
дорого).

Решить — это и есть работа, а не выбор утилиты: слои (процесс в
`Wander.Platform.Windows` за абстракцией, в Core ни слова про robocopy);
прогресс (`OperationTracker` считает элементы и байты, robocopy пишет в stdout —
парсить или неопределённый); отмена = убить процесс, судьба хвоста (`/Z`
продолжает); undo-запись и для внешнего пути (без undo не выпускается);
когда включать (всегда / порог размера / флаг); коды robocopy 0–7 успех,
8+ сбой — замапить в человеческие сообщения.

  выходе» — нет: 1–2 с холодного старта WebView2 каждый раз (TECHDEBT про

  открытый профиль не задевает.
- **[P1] AD2. Корзина открывается долго.** По логам перечисление корзины
  не измеряется: `RefreshShellAsync` заводит `Stopwatch`, но строки
  `Folder listed` для shell-путей нет; косвенно — `nav.refresh` 119 мс и
  `bg.thumb-shell` 691 мс на 69 вызовов при заходе 2026-09-03, то есть ~70
  элементов и доли секунды. Механизм: `WindowsShellNamespace.
  EnumerateRecycleBin` — `Shell.Application` через `dynamic`, на элемент
  6–7 late-bound COM-вызовов (`Name`, `Path`, `IsFolder`, `Size`,
  `ModifyDate`, `GetDetailsOf` ×2), всё до первой строки на экране;
  Проводник рисует строки сразу и добирает колонки. Порядок: (1) строка
  `Folder listed in N ms: K` для shell-путей — и сколько элементов в
  корзине сейчас; (2) если время линейно по элементам — строки сначала
  (имя, путь, папка / файл), вторым проходом размер, даты, «откуда» — как
  `Ratings.StartPass`, правка записей через `ReconcileEntries` без потери
  выделения (правило «список не дёргается»); (3) если дорог сам `Items()`
  — `IShellFolder::EnumObjects` + `IShellFolder2::GetDetailsEx` вместо
  `Shell.Application` (ARCHITECTURE оставила корзину на нём из-за колонок;
  `GetDetailsEx` отдаёт те же по PID, но это переписывание COM — только если
  (2) не хватит). Миниатюры `$R…`-файлов идут в фоне и не блокируют.
- **[P1] AD3. `F2` в дереве папок.** Сегодня `F2` ловит `MainWindow`
  только для списка (`FileList.StartRename()` при выделенной записи);
  `Tree_PreviewKeyDown` знает `Enter`, `Esc`, `Ctrl+↑/↓`; `Delete` /
  `Ctrl+C` / `Alt+Enter` на узле уже идут через `FolderTargeted`. Нужно:
  редактор имени в строке узла (`RenameAdorner` поверх узла, как в списке;
  `Enter` применить, `Esc` отменить), переименование тем же `Rename`
  (гард, лог, undo); после — узел на месте и выделен (`RefreshFor`
  родителя), список не пересобирается, если папка не текущая. Пути,
  которые переписываются вслед — одна функция Core `PathRewrite.Under(
  старый, новый)` с тестом, ко всем сразу: текущая папка и адрес, если
  переименована она или её предок; закладки — путь в `Favorites` (имя
  закладки = имя папки, своего у неё нет: `F2` на закладке — переименование
  папки на диске, путь закладки правится сам, иначе `IsMissing`); история
  (`NavigationStop`), иначе «Назад» ведёт в «папка удалена»;
  `ExpandedPaths`, `RecentPaths`, `ManualViewModes` — той же функцией (Z1
  хочет ключ «путь + дата создания», но до Z1 переписать дёшево). `Ctrl+Z`
  возвращает имя — и пути тоже (тот же `PathRewrite` в undo-действии в
  обратную сторону). Не: корни дисков, узлы shell, внутри архива и корзины.
- **[P0] AD4. Удаление в дереве: узел остаётся, открытой остаётся
  удалённая.** Причина по коду: удаление из дерева идёт через
  `FolderTargeted` → `DeleteSelectedAsync`, после которого `Refresh()`
  перечитывает **текущую** папку; ветки дерева обновляются только тиком
  сторожа текущей папки (`Trees.RefreshFor(here)`) и `F5`. Удалена
  подпапка не текущей папки — узел висит; удалена текущая или её предок —
  листинг падает в `DirectoryNotFoundException` → панель «папка удалена»
  (`SetMissingFolder`), а не шаг вверх. Нужно: после удаления целей из
  дерева — `Trees.RefreshFor` по родителю каждой; если удалённая —
  текущая или предок текущей — перейти в ближайшего живого предка (как
  `Up`), запись истории про удалённую не трогать («Назад» в неё честно
  показывает панель). Правило «куда идти» — чистая функция Core (удалённые
  пути + текущий → цель или «остаться»), тест. `Ctrl+Z` (восстановление) —
  `RefreshFor` родителя, проверить, что уже так. Внешнее удаление текущей
  папки (сторож) — панель «удалена» как есть: там «где папка?» для
  закладок; шаг вверх — только для нашего собственного удаления.
- **[P1] AD5. Журнал: что именно, откуда и куда.** Сегодня
  `ActionJournal` (Core) хранит строки статус-бара (`Status` →
  `Journal.Note`) плюс «Открыта папка …». Итог операции —
  `StatusBatchDone`: «Скопировано: 1 в E:\Video» — счётчик без имён;
  открытие и запуск файлов в журнал не попадают (не строка статуса);
  поимённо `Copy: src -> dst [Ok]` пишет только технический лог. Проверка
  копии 12 ГБ (2026-09-04, 19:55–20:00, `F:\Video\…mkv` → `E:\Video`): в
  логе `Drop: Copy 1 item(s)` и через 5 мин 27 с `Copy: … [Ok]`, ни `WARN`,
  ни `ERROR`, память ровная (~250 МБ ws), три `ui.stall` 150–194 мс в
  момент броска (взвешивание + диалог — TECHDEBT про `Weigh`); итога —
  байты, время, скорость — нет ни в логе, ни в журнале, хотя
  `TransferRate` в `OperationViewModel` их считает. Нужно: (1) журнал
  структурный: запись = время, вид (открыта папка / открыт или запущен
  файл / скопировано / перемещено / переименовано / в корзину / удалено /
  восстановлено / создано / извлечено / отменено / запущено действие /
  ошибка), заголовок и элементы — «Скопировано в E:\Video — 1 файл, 12,3
  ГБ, 5 мин 27 с», ниже по строке на элемент; переименование — парами
  «было → стало»; предел на операцию (первые 50 и «ещё N»), общий предел —
  по операциям, не по строкам; (2) источник — результаты, которые уже в
  руках там, где собирается строка статуса: `BatchExecutor` отдаёт статус
  на элемент, `DeleteSelectedAsync` — `results`, переименование — `plan`,
  открытие — вызовы `Shell.Open` / `OpenWith` / временная копия; строки
  статуса, у которых появился структурный двойник, больше не зеркалятся
  (иначе дубли), остальные (ошибки, поиск, буфер) — как сейчас; (3) в
  технический лог — одна строка итога операции: элементы, байты, секунды,
  МБ/с; (4) окно журнала — тот же текст, отступы у элементов, без
  фильтров. Решить до кода: хранить ли журнал между запусками (сейчас
  файл на запуск, только если открывали; TECHDEBT про ротацию) —
  предложение: нет, журнал сеанса.
- **[P2] AD6. Прогресс в строке состояния — прижать вправо.** Причина в
  XAML: элемент операций — последний ребёнок `DockPanel` строки состояния
