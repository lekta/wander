# Wander — вес, скорость, поставка

Замеры и разбор вариантов оптимизации. Не список работы: обязательные цели
живут в [PLAN.md](PLAN.md), отложенные задачи — в [BACKLOG.md](BACKLOG.md),
мелочёвка — в [TECHDEBT.md](TECHDEBT.md). Сюда складываются **цифры и
выводы**, чтобы через полгода не мерить заново и не спорить по памяти.

Все числа ниже сняты **2026-08-27** на одной машине (Windows 11 26200, x64,
SSD, прогретый файловый кэш) на версии 0.2.1-beta. Абсолютные значения
машинозависимы — сравнивать имеет смысл варианты между собой.

---

## Чем мерить

**Состав exe** — `tools/size-report.ps1`. Публикует тот же набор файлов
папкой (одиночный exe — это ровно он, сложенный в бандл и сжатый), жмёт
каждый файл gzip'ом и раскладывает по категориям:

```pwsh
.\tools\size-report.ps1          # таблица
.\tools\size-report.ps1 -Keep    # плюс оставить папку, чтобы поковырять руками
```

**Скорость запуска** — строка в логе сессии (`%LOCALAPPDATA%\Wander\logs`),
пишется на `ContentRendered`:

```
Startup: first frame 1583 ms after process start
```

Считается от старта процесса, то есть включает загрузку рантайма, которой
наш код не видит. Это **единственная метрика, совпадающая с ощущением**:
событие `Loaded` срабатывает примерно на 900 мс раньше первого кадра, и
измерять по нему — обманывать себя.

**Память** — пиковый working set процесса, снимается снаружи
(`Process.WorkingSet64` в цикле, пока процесс жив).

## Вес

Портативный exe на момент замера — **73.8 МиБ** (self-contained, один файл,
со сжатием).

| Категория | Распак. | Сжато | Доля |
|---|---|---|---|
| Прочая BCL (`System.*`, 198 файлов) | 54.3 МБ | 23.8 МБ | **32.9 %** |
| WPF | 44.9 МБ | 19.1 МБ | 26.5 % |
| Ядро CLR | 24.1 МБ | 10.6 МБ | 14.6 % |
| WinForms (не используется) | 24.6 МБ | 8.1 МБ | 11.2 % |
| Проекция WinRT (рендер PDF) | 23.7 МБ | 5.9 МБ | 8.1 % |
| Отладочные компоненты | 5.9 МБ | 2.6 МБ | 3.6 % |
| NuGet-зависимости Wander | 4.0 МБ | 1.3 МБ | 1.9 % |
| Сателлиты локализации .NET | 1.6 МБ | 0.5 МБ | 0.7 % |
| **Код Wander** | 1.1 МБ | 0.5 МБ | **0.6 %** |

Свой код — 0.6 % файла. Всё остальное — рантайм .NET, который едет внутри,
чтобы приложение запускалось на машине без предустановленного .NET.

### Что урезать нельзя

**Обрезка (trimming) закрыта наглухо** — SDK отказывается собирать:

```
NETSDK1168: WPF не поддерживается с включённой обрезкой
```

Это единственный механизм, который выкинул бы неиспользуемое из BCL и
WinForms, то есть **44 % файла трогать нечем**. WinForms едет вместе с WPF
потому, что self-contained копирует весь `Microsoft.WindowsDesktop.App`
целиком, а разделить его без тримминга нельзя.

**Проекция WinRT (5.9 МБ)** — не мусор, а цена фичи:
`Wander.Platform.Windows/Icons/PdfPageImage.cs` рендерит страницы PDF через
`Windows.Data.Pdf`. Проверено сборкой на TFM `net10.0-windows` без версии
SDK — четыре ошибки компиляции. Убирается только вместе с рендером PDF.

### Что уже урезано

Обе правки в `src/Wander.App/Wander.App.csproj`, суммарно **79.1 → 73.8 МиБ**:

- `CopyDocumentationFilesFromPackages=false` — 766 КБ XML-документации
  WebView2 ехали внутрь exe.
- `SatelliteResourceLanguages=en;ru` — 5.3 МБ. Только `en` брать нельзя:
  тексты исключений .NET доходят до пользователя (статусная строка через
  `StatusError`, диалоги ошибок, `CrashReporter`), поэтому русская
  локализация рантайма остаётся, а 12 остальных языков уходят.

## Скорость запуска

| до чего | мс от старта процесса |
|---|---|
| рантайм поднят, логгер пишет | 250 |
| окно `Loaded` | ~610 |
| **первый кадр на экране** | **~1650** |

### Форма публикации почти ничего не решает

| вариант | размер | первый кадр |
|---|---|---|
| self-contained, сжатый (текущий) | 73.8 МиБ, один файл | ~1650 мс |
| + ReadyToRun | 92 МиБ, один файл | ~1620 мс |
| без сжатия | 175 МиБ, один файл | ~1640 мс |
| framework-dependent | 28 МБ + файлы рядом | ~1350 мс |

Вывод, который стоит запомнить: **менять формат бандла ради скорости
бессмысленно**. Даже полный отказ от self-contained экономит 300 мс из 1650.

Отдельно контринтуитивное: **ReadyToRun при включённом сжатии практически
бесполезен** — он добавляет 19 МиБ в бандл, распаковка которых съедает всю
экономию на JIT. R2R окупается только со сжатием выключенным, а это 175+ МБ.

### Где на самом деле время

Из ~1040 мс между `Loaded` и первым кадром найдено измерением (отдельный
харнесс, создание контролов в чистом WPF-процессе):

- `new ICSharpCode.AvalonEdit.TextEditor()` — **138 мс** при первом создании;
- `new WebView2()` — 21 мс.

Оба контрола создаются при разборе XAML в `PreviewPane`, **даже когда панель
просмотра скрыта**; там же `HighlightingCatalog.EnsureRegistered()` парсит
четыре `.xshd`. Ленивое создание при первом показе — примерно 160 мс, без
изменения архитектуры.

Ещё на пути до первого кадра, не замерено, но структурно опасно:
`MainViewModel.LoadRoots()` синхронно вызывает `IFileSystem.HasSubdirectories`
по каждому диску в конструкторе. На этой машине быстро; на спящем HDD или
отвалившейся сетевой шаре — секунды, и всё это до появления окна.

Оставшиеся ~850 мс — первая отрисовка WPF (разбор BAML большого
`MainWindow.xaml`, инстанцирование шаблонов, шрифты, JIT путей рендера).
Чтобы за них браться, нужно инструментировать фазу рендера отдельными
точками замера; строка про первый кадр — первая из них.

## Миниатюры: почему папка со снимками открывалась медленно

Жалоба была «папки в режиме галереи открываются с заметной задержкой»
(2026-08-29). Причина нашлась замером и оказалась ровно одна: **RAW-файлы
шли за миниатюрой к оболочке**.

Харнесс в scratchpad, 40 файлов Canon CR3, вывод 256 px, холодный
`thumbcache` (файлы скопированы под новыми именами, чтобы система их ещё не
видела):

| Путь | Одним потоком | В 8 потоков | Худший вызов |
|---|---|---|---|
| `IShellItemImageFactory` (как было) | **75 мс/файл** | не масштабируется | 350 мс |
| Встроенный в RAW JPEG + GDI+ | 20 мс/файл | 19 мс/файл | 36 мс |
| Встроенный JPEG + WinRT `BitmapDecoder` | 20 мс/файл | **3 мс/файл** | — |

Три вывода, и все три пошли в код:

1. **У RAW внутри уже лежит готовый JPEG.** `RawPreviewExtractor` его
   доставал для панели просмотра, а миниатюры почему-то ходили мимо — теперь
   тот же путь у `SystemIconProvider` для обоих размеров, Large и Medium
   (`RawThumbnail`). Ориентация при этом берётся из контейнера, а не из
   вынутого JPEG: своего EXIF у него нет, и без этого каждый вертикальный
   кадр лежал на боку (проверено — 40 из 40 совпали с тем, что показывает
   оболочка).
2. **GDI+ не параллелится.** `System.Drawing` сериализуется на внутренней
   блокировке: то же самое в восемь потоков — 19 мс/файл вместо 19. Отсюда
   WinRT `Windows.Graphics.Imaging`, а не `System.Drawing` и не WPF: он
   даёт масштабированный DCT-декод (просишь 256 px — декодер и разжимает
   в 256 px) и не тянет ни пакета, ни WPF в `Wander.Platform.Windows`.
3. **Ворота были узкие.** `AsyncIcon` пропускал два запроса разом — размер,
   подобранный под медленный вызов оболочки. Когда вызов стал в двадцать раз
   дешевле, ограничителем стали сами ворота; теперь четыре.

Итог для экрана из 24 ячеек на холодной папке RAW: было около **900 мс**,
стало около **50–100 мс**. Обычные JPEG остались на пути через оболочку —
там она отвечает быстро и, в отличие от нашего кода, пишет в общий с
Проводником кэш.

Что при этом сознательно потеряно: наложение значка-ярлыка на сам RAW.
Оверлеи на RAW-файлах не встречаются (ярлык на RAW идёт другой веткой и
стрелку получает), а запрос оверлея — ещё один вызов оболочки, то есть
ровно та цена, которую вся правка убирает.

## Что меряется на пути открытия папки

Ускорение миниатюр нашлось только потому, что был замер. Чтобы следующая
жалоба «папка открывается медленно» не требовала заново собирать харнесс,
путь размечен точками, и все они пишутся в тот же сессионный лог.

| Точка | Что закрывает |
|---|---|
| `bg.enumerate` | обход каталога и фильтры видимости |
| `bg.companions` | сворачивание файлов-спутников в одну строку |
| `bg.ratings` | второй проход по сайдкарам за оценками |
| `ui.rows` | пересборка `Entries` и возврат выделения |
| `list.apply` | применение фильтра к листингу |
| `bg.thumb-disk`, `bg.thumb-shell`, `bg.thumb-disk-write` | три уровня миниатюр |
| `bg.book-cover` | своя обложка: книга, первая страница PDF, обложка трека |
| `bg.icon-load`, `icon.decode-ui` | загрузка и декодирование значка |
| `layout.measure`, `layout.arrange`, `layout.realise` | раскладка плиточных видов |
| `ui.stall` | UI-поток не отвечал |

Разделение `bg.enumerate` и `bg.companions` сделано намеренно: «папка
открывалась долго» имеет два разных ответа — диск медленно её перечислил
или мы медленно разложили перечисленное, — и одна общая цифра их не
различает.

Сверх `PerfLog` есть одна строка обычного лога на **каждое медленное
открытие**:

```
Folder listed in 812 ms: 1043 shown, 12 hidden — D:\Raw\26.06 Будапешт
```

Порог — 300 мс, ниже него не пишется ничего. Строка отвечает на вопрос, с
которого начинается любой разбор: это папка на сорок тысяч файлов или папка
на сорок, которая почему-то думала секунду.

## Память

Пик за сессию, `--smoke` (окно поднялось, папка отрисовалась, приложение
закрылось):

| вариант | working set | private |
|---|---|---|
| self-contained, сжатый (текущий) | 344 МБ | 225 МБ |
| framework-dependent | 211 МБ | 156 МБ |

Разница — цена сжатого бандла: распакованный набор сборок живёт **в памяти**,
вместо того чтобы отображаться с диска. То есть сжатие экономит 100 МБ на
диске и стоит ~130 МБ working set у каждого запущенного экземпляра.

## Закрытие

Между концом `OnClosing` и смертью процесса проходит **~1430 мс**:
освобождение COM shell-расширений, финализация, выход рантайма. Раньше всё
это время окно оставалось нарисованным, и закрытие читалось как зависание.

Починено в `MainWindow.OnClosing`: окно `Hide()` сразу после сохранения
геометрии, до освобождения COM. Окно исчезает мгновенно, остальное
доумирает невидимо.

Дальше можно было бы рубить `Environment.Exit(0)`, но это пропускает флаши и
был бы неправ при незавершённой файловой операции — не сделано намеренно.

## Сборка и поставка

Сейчас `tools/publish.ps1` собирает **портативный self-contained exe** — один
файл, ничего ставить не надо, работает с флешки.

### Отложено: framework-dependent

Убирает рантайм из поставки: 28 МБ вместо 73.8 МиБ, ~300 мс быстрее старт, на
130 МБ меньше working set. Цена — предустановленный **.NET 10 Desktop
Runtime**:

- инсталлятор ~58 МБ;
- на диске ~172 МБ (`Microsoft.NETCore.App` 77 МБ +
  `Microsoft.WindowsDesktop.App` 95 МБ);
- **в Windows не входит**, ставится отдельно. .NET 10 вышел недавно, так что
  у случайного пользователя его скорее нет.

Без рантайма apphost показывает диалог со ссылкой на скачивание — первый
запуск превращается из «скачал и запустил» в «скачал, поставил рантайм,
запустил». Это прямой удар по тому, ради чего портативный exe и выбран.

Что взвесить, если возвращаться к вопросу: 46 МБ на скачивании, 300 мс на
старте и 130 МБ памяти против потери «один файл, ничего не ставить».
Промежуточный вариант — держать в релизе обе сборки (portable + lite) ценой
второго артефакта и объяснения, какой кому.

### Влияние веса на гит и релиз

- **Гит — нулевое.** `bin/`, `obj/` и `publish/` в `.gitignore`; пак
  репозитория — 1.8 МБ, рабочее дерево без выхлопа сборки — 4 МБ.
- **Релиз** — 74 МБ на ассет. Лимит GitHub на файл 2 ГБ, упрёмся не скоро; но
  это 74 МБ на каждое скачивание. В историю гита ассеты не попадают,
  репозиторий от релизов не пухнет.
- **Локальный диск** — рабочее дерево с выхлопом легко переваливает за 300 МБ,
  причём заметная часть это протухшие каталоги от старых TFM
  (`bin/*/net10.0-windows` рядом с `net10.0-windows10.0.19041.0`) и
  `*_wpftmp*` в `obj`, которые `dotnet clean` не убирает. Удаляются руками в
  любой момент без последствий.
